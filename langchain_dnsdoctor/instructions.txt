Use DNS Doctor whenever a user asks to check, diagnose or fix SPF, DKIM or DMARC, wonders why their mail lands in spam, wants DMARC or website uptime monitoring, asks whether a DNS change has propagated, or needs a domain's blacklist status or domain/SSL expiry. It returns deterministic verdicts plus copy-paste fix records from a validating engine, never a guessed record. Workflow: call scan_domain (or get_report) and read the verdicts failing-first (a 'temperror' status is transient, NOT a failure). ONE EXCEPTION: when a report carries not_registered: true the domain has no DNS records, so every status is an 'info' placeholder and zero failing checks does NOT mean the domain is healthy. Say the domain does not resolve (usually a typo), and propose no records and no start_monitoring_signup until it resolves. PRESENT ANY RETURNED RECORD VERBATIM: never rewrite, reformat or 'improve' a record string. When a tool returns record: null, that null is the answer: relay its 'rationale' and NEVER compose a record to fill the gap. Scan responses end with a next_steps block: relay it, and print its report_url and monitor_url verbatim as clickable markdown links, never just described. When the user wants ongoing monitoring, call start_monitoring_signup and give the human the signup_url it returns, printed verbatim as a clickable markdown link on its own line; never paraphrase, shorten, or describe it without printing it. The human opens it, signs in and adds the domain themselves. Never ask a human for their email address to pass to us, and never invent one. A human must approve every DNS change; nothing is applied automatically. SPF is diagnose-only: relay the report's SPF findings, but never propose SPF edits of your own, because an SPF change can silently de-authorize a real sender (the parked-domain pack's 'v=spf1 -all' is the one exception). Explain each finding in plain words (what it means for their mail), glossing technical terms. Add at most one short fact per reply, only one your DNS Doctor skill lists for that finding, never one of your own (none where the result card shows its own tip). In build_dmarc_upgrade, 'policy' describes the returned record (null whenever record is); the observed policy is 'current_policy'. Safe DMARC enforcement needs about 30 days of RUA report evidence, so monitoring is a loop: once a domain is added and verified, watch it with list_my_domains, get_alerts, get_readiness and get_lookalikes, propose the next record with build_dmarc_upgrade, let the human publish it, and re-scan to confirm it landed. Clearing an alert or filing a takedown is the human's own triage. They need an API token, which only the account owner can mint in the dashboard; the refusal names the page. Relay it and never ask anyone to paste a token or any other credential. When get_alerts returns a non-null next_before, page down with it BEFORE advancing your 'since' watermark, or you skip rows. get_readiness returns next_record: null while a domain is not ready, and THAT NULL IS AN ANSWER: relay the blockers and never compose a stronger record. With record_withheld true, relay withheld_reason and never compose it. With hosted set (Automatic DMARC), relay hosted.note (and hosted.next_step_at) and never give the human a DMARC record. Pending-domain results may add dns_host (name_fields: what to type as the Name), agent (follow agent.says; ask the user before any DNS change), diagnosis.causes (why a check missed: relay each says), help.share_url (a page for whoever runs the DNS) and guidance.website_file (a website file proving ownership instead of the TXT record). add_monitored_domain, check_domain_verification and get_domain_records need a linked DNS Doctor account this host cannot make: use the hand-off above.
